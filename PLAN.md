## 0. Поточний стан і ключове рішення

Зараз бот — "тонкий" AI-консультант:
- `webhook_bot.py` — Flask + webhook, event loop у фоновому потоці
- `groq_client.py` — Groq API, історія чату **in-memory** (зникає при рестарті)
- Жодної бази даних, кнопок, фонових задач

**Ключове рішення: салон вже працює на Altegio** (alteg.io) — там живуть записи, розклад, послуги, ціни, клієнтська база і програма лояльності.

Тому архітектурний принцип усього плану:

> **Altegio — єдине джерело правди** для записів, слотів, послуг, цін, клієнтів і бонусів.
> **Бот — Telegram-інтерфейс до Altegio** + власна маленька БД лише для того, чого в Altegio немає.

Що це знімає з плану:
- ❌ Власні таблиці слотів/послуг/цін/записів — беремо з Altegio API
- ❌ Власна бонусна система — Altegio має loyalty API
- ❌ Питання "яка CRM?" — Altegio і є CRM, клієнти створюються прямо там
- ❌ Адмін-механіка генерації слотів — адміністратор веде розклад в Altegio як звик

Що все одно потрібно своє:
- ✅ Маленька БД (Supabase, безкоштовний tier): зв'язка Telegram ↔ Altegio, картки улюбленців, черга сповіщень, оцінки, фото до/після, історія AI-чату
- ✅ Планувальник (cron) для Telegram-нагадувань (Altegio шле SMS/push у своєму додатку, але не в наш Telegram-бот)
- ✅ Приймання вебхуків від Altegio (запис створили/перенесли/скасували на сайті чи адміністратором → бот одразу в курсі)

## Altegio API — що використовуємо

Документація: https://developer.alteg.io/en

| Потреба бота | Механізм Altegio |
|---|---|
| Вільні слоти, дати, майстри | Online Booking API: `book_dates`, `book_times`, `book_staff`, `book_services` (публічні, без user token) |
| Створити запис | Online Booking API: `book_record` |
| Мої записи / перенести / скасувати | Business API: records клієнта (get / update / delete) |
| Клієнти: створити, знайти по телефону, оновити | Business API: clients (+ custom fields) |
| Послуги та ціни | Business API / Online Booking: services з цінами |
| Локації (філії) | companies/locations |
| Бонуси | Loyalty API: баланс, транзакції |
| Події "запис створено/змінено/видалено" | WebHooks (Settings → System settings → WebHook → наш endpoint) |
| Візит відбувся (attendance) | статус record-а в Altegio (адмін відмічає у своєму інтерфейсі як звик) |

**Авторизація:** `Authorization: Bearer <partner_token>, User <user_token>`. Отримати:
1. Partner token (доступ до API / маркетплейс Altegio)
2. User token користувача з потрібними правами
3. `company_id` кожної філії

### ⚠️ Перевірити на старті (Фаза 0, до написання коду)
1. **Тариф/доступ до API** — чи відкритий API на поточному тарифі салону.
2. **Улюбленці в Altegio** — чи доступні картки тварин через API (в документації явно не описано). Якщо ні → зберігаємо улюбленців у своїй БД, а в Altegio-записі передаємо ім'я/породу в коментарі.
3. **Loyalty API** — чи використовує салон бонусну програму Altegio і чи читається баланс по API. Якщо ні → власні таблиці бонусів (запасний варіант описаний у Фазі 6).
4. **Правило 24 год** — в Altegio є власне налаштування вікна онлайн-скасування; узгодити, щоб бот і сайт поводились однаково.

## Архітектурні рішення

### БД: Supabase (безкоштовний tier)
- **Supabase** = хмарний Postgres + веб-панель. Нічого не треба хостити самим; адміністратор може дивитись дані (улюбленці, оцінки) прямо в браузері.
- Підключення — **тільки через `supabase-py` (REST, HTTPS)**, НЕ напряму до Postgres: безкоштовний PythonAnywhere блокує сирі TCP-з'єднання (порт 5432), а HTTPS через проксі працює.
- Схему таблиць створюємо через SQL Editor у панелі Supabase (SQL-скрипт тримаємо в репо: `db/schema.sql`), тому SQLAlchemy/Alembic не потрібні.
- Ключі: `SUPABASE_URL` + `SUPABASE_SERVICE_KEY` у `.env` (service key, бо звертається тільки наш бекенд; Row Level Security можна не вмикати).
- Зберігає ТІЛЬКИ те, чого немає в Altegio (модель нижче).

### Scheduler: PythonAnywhere Scheduled Task → HTTP endpoint
- Endpoint `POST /cron/<CRON_SECRET>` у Flask, викликається кожні 10–15 хв (PythonAnywhere Scheduled Task на платному тарифі або безкоштовний зовнішній cron типу cron-job.org).
- Всі заплановані сповіщення — в таблиці `notifications` (`pending`/`sent`), рестарти нічого не гублять.

### Вебхуки Altegio: endpoint `POST /altegio/webhook`
- Приймає події record created/updated/deleted.
- Синхронізує стан: перепланувати нагадування при переносі, скасувати їх при видаленні запису, надіслати клієнту підтвердження якщо запис створив адміністратор по телефону.
- Перевірка автентичності (секрет в URL + звірка даних через API).

### UI бота: Inline-кнопки + ConversationHandler
- Головне меню — `ReplyKeyboardMarkup`; флоу (запис, анкета, оцінка) — `InlineKeyboardMarkup` + `CallbackQueryHandler` + `ConversationHandler`.
- Стан ConversationHandler in-memory; чернетка анкети додатково в БД (`draft_json`), щоб рестарт не втрачав прогрес.

### Ролі
- `ADMIN_CHAT_IDS` у `.env` — сповіщення (низька оцінка, незаповнена анкета, "потрібна допомога").
- Адмін-функції в боті — мінімальні (фото до/після, рекомендації майстра). Все інше адміністратор робить в Altegio.

## Модель даних у Supabase (мінімальна)

```
clients        id, tg_user_id (unique), altegio_client_id, phone, name,
               registration_done (bool), draft_json (чернетка анкети),
               last_promo_at (anti-spam)

pets           id, client_id → clients, name, breed, birth_date, weight,
               allergies, behavior_notes, photo_file_id,
               rabies_vaccine_date, vaccine_photo_file_ids (json),
               altegio_pet_id (nullable — якщо Altegio віддає тварин по API)

tracked_records id, altegio_record_id (unique), client_id, pet_id,
               starts_at, service_title, location_title, status,
               raw_json (останній стан з Altegio/вебхука)
               -- локальний "кеш" записів: щоб планувати нагадування
               -- і зв'язувати запис ↔ улюбленець ↔ оцінка

visit_extras   id, altegio_record_id, groomer_recommendations (text),
               next_visit_weeks (int), photo_before_ids (json), photo_after_ids (json)
               -- те, чого в Altegio немає: фото до/після + рекомендації майстра

ratings        id, altegio_record_id, service_stars (1–5), groomer_stars (1–5),
               comment, created_at

notifications  id, client_id, type (reminder_2h / thanks_rating / rebook_nudge /
               birthday / vaccine / form_incomplete / custom),
               payload_json, send_after, status (pending/sent/failed), sent_at

chat_messages  id, client_id, role, content, created_at
               -- історія AI-чату (переживає рестарти, обрізаємо до ~20 останніх)
```

Telegram-фото зберігаємо як `file_id` (Telegram тримає файли вічно).
Записи, слоти, послуги, ціни, бонуси — **НЕ дублюємо**, читаємо з Altegio (крім легкого кешу `tracked_records` для нагадувань).

9. Роутинг: кнопки меню → handler-и; інший текст → Groq (як зараз).

**Критерій готовності:** тестовий скрипт через `services/altegio.py` дістає реальні послуги/слоти салону; вебхук від Altegio долітає і логується; меню працює; AI-чат не зламаний.

### 🟨 Фаза 1 — Реєстрація клієнта + картки улюбленців
> Код готовий. Лишилось: виконати `db/migrations/001_phase1_altegio_company_id.sql` у Supabase і прогнати критерій готовності на живому боті.

**Флоу анкети (ConversationHandler):**
1. `/start` → якщо tg_user_id немає в БД → "Давайте знайомитись!" → ім'я → телефон (кнопка `request_contact`).
2. По телефону шукаємо клієнта в Altegio (`find_client_by_phone`): знайшли → прив'язуємо `altegio_client_id`; ні → `create_client()` в Altegio. **Клієнт одразу в CRM** — окрема синхронізація не потрібна.
3. Цикл додавання улюбленця: ім'я → порода → дата народження → вага → алергії → особливості поведінки → фото улюбленця (опційно). Дублюємо ключове (порода, вага, особливості) в коментар/custom fields клієнта в Altegio — щоб адміністратор бачив у своєму інтерфейсі. **Вакцинацію в анкеті не питаємо:** дату веде адміністратор у картці клієнта Altegio, окрема автоматизація перевіряє відсутність/прострочення і сповіщає адміна.
4. "Додати ще одного улюбленця?" → так/ні. Кожен крок зберігає чернетку в `draft_json`.

**Картки улюбленців (`🐾 Мої улюбленці`):** список → картка (фото + поля) → `✏️ Редагувати` поле за полем (зміни синхронізуємо в Altegio).

**Контроль заповнення (для адміністратора):**
- Сценарій "адмін дає посилання на бота перед першим візитом": при першому `/start` створюється notification `form_incomplete` з `send_after = сьогодні 21:00`; cron: якщо `registration_done == False` → повідомлення адмінам "Клієнт X не заповнив анкету".

**Критерій готовності:** новий користувач проходить анкету, клієнт з'являється в Altegio (видно в інтерфейсі салону), улюбленці в локальній БД, адмін отримує сповіщення про незаповнені анкети.

### ⬜ Фаза 2 — Онлайн-запис на грумінг ⭐ головна функція

**Все через Altegio Online Booking API — ніяких власних слотів.**

**Флоу запису (`📅 Записатись`):**
1. Вибір улюбленця (якщо один — автоматично).
2. Вибір локації (з `get_locations()`; у картці — адреса + гео-пін).
3. Вибір послуги з цінами (`get_services()` для company_id). Пункт меню "💰 Дізнатись вартість" — той самий флоу без завершення запису. Якщо ціни в Altegio залежать від розміру — це різні послуги/варіанти там, бот просто показує список; за вагою улюбленця можна підсвічувати рекомендований варіант.
4. Вільні дати (`book_dates`) → вільні часи (`book_times`).
5. Підтвердження: "🐶 Барні · Комплекс · Локація X · 15.07 о 14:00 · 800 грн" → `✅ Підтвердити` → `create_record()` (в коментар запису — ім'я/порода/особливості улюбленця, щоб майстер бачив в Altegio).
6. Після успіху: збереження в `tracked_records`, планування нагадувань (Фаза 4). Подвійне бронювання неможливе — слоти контролює Altegio.

**Записи, зроблені НЕ через бота** (по телефону, на сайті): прилітають вебхуком → якщо клієнт відомий по телефону → додаємо в `tracked_records`, шлемо підтвердження в Telegram і теж плануємо нагадування. Це великий плюс: бот покриває нагадуваннями ВСІ записи салону, не тільки свої.

**Критерій готовності:** запис із бота з'являється в календарі Altegio; запис, створений адміністратором в Altegio, з'являється у клієнта в боті.

### ⬜ Фаза 3 — Управління записами

**`🗓 Мої записи`** — майбутні записи (з `tracked_records`, звірені з Altegio API):
- `🔁 Перенести` — якщо до візиту **> 24 год**: вибір нового слота → `move_record()` (або cancel+create). Інакше: "Перенести можна не пізніше ніж за 24 години — зв'яжіться з адміністратором" + кнопка 🆘.
- `❌ Скасувати` — те саме правило 24 год + підтвердження → `cancel_record()` → сповіщення адмінам. Узгодити з налаштуванням вікна скасування в самому Altegio.
- `🔄 Повторити останній запис` — останній завершений візит (улюбленець + послуга + локація) → одразу на вибір дати/часу.

**Критерій готовності:** перенос/скасування відображаються в календарі Altegio миттєво; правило 24 год працює; повтор — 2–3 натискання.

### ⬜ Фаза 4 — Автоматичні нагадування + оцінки

Через `notifications` + cron + вебхуки Altegio.

**При появі запису в `tracked_records`** (з бота АБО вебхуком):
- `reminder_2h`: `send_after = starts_at − 2.5 год` — "Нагадуємо: сьогодні о 14:00 чекаємо Барні 🐶 Адреса: …".
- Перенос запису (вебхук) → нагадування перепланувати; скасування → видалити pending-сповіщення.

**Після візиту:**
- Cron перевіряє через Altegio API attendance/статус record-ів, що вже минули. Візит відбувся → `thanks_rating` через ~1 год: "Дякуємо за візит! 💛".
- **Флоу оцінки:** "Оцініть сервіс" `⭐1…5` → "Оцініть роботу грумера" `⭐1…5`:
  - Обидві **5** → "Будемо вдячні за відгук на Google Maps" + кнопка (`GOOGLE_MAPS_REVIEW_URL`).
  - Будь-яка **≤ 3** → миттєво адмінам: "⚠️ Низька оцінка від {клієнт} ({телефон}): сервіс X★, грумер Y★. Візит: {деталі}. Зв'яжіться з клієнтом."
  - Опційний текстовий коментар.

**Rebook-нагадування:**
- Після візиту планується `rebook_nudge`: `send_after = visit + next_visit_weeks` (рекомендація майстра з Фази 5, дефолт 6 тижнів) — "Барні час на грумінг 🐩 Записатись?" + кнопка у флоу запису. Скасовується, якщо клієнт уже записався (бот бачить всі записи через вебхуки).

**Критерій готовності:** повний цикл на тестовому записі: створення → нагадування → візит відмічений в Altegio → подяка → оцінка → (Google Maps / алерт адміну) → nudge.

### ⬜ Фаза 5 — Історія грумінгу + рекомендації майстра

**Клієнт (`✂️ Історія`):** вибір улюбленця → минулі візити (records з Altegio: дата, послуга, локація, майстер) → деталі + те, що в `visit_extras`: фото "до/після", рекомендації майстра, "наступний візит через N тижнів".

**Адмін/грумер (`/admin` → "візити за сьогодні"):** список сьогоднішніх records з Altegio → вибрати → надіслати фото "до"/"після" (`file_id`) → текст рекомендацій → "наступний візит через N тижнів" (кнопки 4/6/8/12). Після заповнення клієнту летить "Рекомендації від майстра щодо Барні: …" (це N живить rebook_nudge).

**Критерій готовності:** грумер оформлює візит з телефону за 1–2 хв; клієнт бачить фото і рекомендації в історії.

### ⬜ Фаза 6 — Бонусна програма

**Основний варіант — Loyalty API Altegio:**
- `🎁 Бонуси`: баланс з `get_loyalty_balance()` + умови програми (текст у налаштуваннях).
- Нарахування/списання відбуваються в Altegio при оплаті — бот лише показує.
- Пуші про операції: якщо Altegio шле вебхуки фінансових операцій — з них; інакше cron порівнює баланс із збереженим і шле "➕ Нараховано 80 бонусів. Баланс: 230".

**Запасний варіант** (якщо салон не використовує loyalty Altegio або API його не віддає): власні таблиці `bonus_accounts`/`bonus_ops`, нарахування X% після візиту, ручні операції адміна через `/admin`.

**Критерій готовності:** клієнт бачить актуальний баланс; про зміну балансу приходить пуш.

### ⬜ Фаза 7 — Персональні пропозиції та автоматизація

Нові типи в `notifications` + cron:

- **День народження улюбленця**: щоденна перевірка `pets.birth_date` → "🎂 Барні сьогодні 3 роки! Даруємо знижку 20% цього тижня" (текст/розмір — у налаштуваннях; знижку адмін застосовує в Altegio вручну).
- **Ревакцинація**: ~~`rabies_vaccine_date + 1 рік − 2 тижні`~~ дату вакцинації бот не збирає (Фаза 1) — вона в картці клієнта Altegio, прострочення вже контролює окрема автоматизація зі сповіщенням адміну. Якщо захочемо нагадувати самому клієнту в Telegram — читати дату з Altegio.
- **"Маємо вікно завтра"**: `/admin` → "запропонувати вільний слот" → бот бере вільні слоти з Altegio на завтра → шле пропозицію клієнтам з простроченим rebook по цій локації. Anti-spam: не частіше 1 пропозиції на тиждень (`last_promo_at`).
- **Поради від грумера** (косметика, частота догляду) — це рекомендації Фази 5, окремої механіки не треба.

**Критерій готовності:** тригери спрацьовують на тестових даних, anti-spam працює.

### ⬜ Фаза 8 — AI-помічник 2.0

1. **Контекст у промпт**: перед викликом Groq підставляти живі дані з Altegio — послуги з цінами, адреси філій, улюбленців клієнта. Дешево, дає 80% ефекту (і прибирає нинішнє "щодо цін звертайтесь до адміністратора").
2. **Function calling (Groq tool use)**: інструменти `get_free_slots(location, date)`, `get_price(service)`, `start_booking()` — AI відповідає "завтра є вікно о 15:00, записати?" і кнопкою веде у флоу запису.
3. **Корисні поради**: розширити `SYSTEM_PROMPT` базою порад (догляд між грумінгами, розчісування, купання, сезонні) + застереження "не заміна ветеринару" для health-питань.
4. Історію чату — в `chat_messages` (БД) замість in-memory, обрізати до ~20 повідомлень.

**Критерій готовності:** AI називає реальні ціни/адреси/слоти з Altegio і не вигадує.

### ⬜ Фаза 9 — Зв'язок з адміністратором

Маленька, можна будь-коли після Фази 0:
- `🆘 Допомога` → "Опишіть питання" → пересилання всім `ADMIN_CHAT_IDS` з ім'ям/телефоном клієнта.
- Адмін відповідає **reply-ем** → бот доставляє відповідь клієнту (мапінг `forwarded_msg_id → client_id` у БД).

**Критерій готовності:** двосторонній діалог клієнт ↔ адмін через бота.
