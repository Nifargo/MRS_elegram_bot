## 0. Поточний стан і ключове рішення

Зараз бот — "тонкий" AI-консультант:
- `webhook_bot.py` — Flask + webhook, event loop у фоновому потоці
- `groq_client.py` — Groq API, історія чату **in-memory** (зникає при рестарті)
- Жодної бази даних, кнопок, фонових задач

**Ключове рішення: салон вже працює на Altegio** (alteg.io) — там живуть записи, розклад, послуги, ціни, клієнтська база і програма лояльності.

Тому архітектурний принцип усього плану:

> **Altegio — єдине джерело правди** для записів, слотів, послуг, цін, клієнтів і бонусів.
> **Бот — Telegram-інтерфейс до Altegio** + власна маленька БД лише для того, чого в Altegio немає.

Що це знімає з плану:
- ❌ Власні таблиці слотів/послуг/цін/записів — беремо з Altegio API
- ❌ Власна бонусна система — Altegio має loyalty API
- ❌ Питання "яка CRM?" — Altegio і є CRM, клієнти створюються прямо там
- ❌ Адмін-механіка генерації слотів — адміністратор веде розклад в Altegio як звик

Що все одно потрібно своє:
- ✅ Маленька БД (Supabase, безкоштовний tier): зв'язка Telegram ↔ Altegio, картки улюбленців, черга сповіщень, оцінки, фото до/після, історія AI-чату
- ✅ Планувальник (cron) для Telegram-нагадувань (Altegio шле SMS/push у своєму додатку, але не в наш Telegram-бот)
- ✅ Приймання вебхуків від Altegio (запис створили/перенесли/скасували на сайті чи адміністратором → бот одразу в курсі)

## Altegio API — що використовуємо

Документація: https://developer.alteg.io/en

| Потреба бота | Механізм Altegio |
|---|---|
| Вільні слоти, дати, майстри | Online Booking API: `book_dates`, `book_times`, `book_staff`, `book_services` (публічні, без user token) |
| Створити запис | Online Booking API: `book_record` |
| Мої записи / перенести / скасувати | Business API: records клієнта (get / update / delete) |
| Клієнти: створити, знайти по телефону, оновити | Business API: clients (+ custom fields) |
| Послуги та ціни | Business API / Online Booking: services з цінами |
| Локації (філії) | companies/locations |
| Бонуси | Loyalty API: баланс, транзакції |
| Події "запис створено/змінено/видалено" | WebHooks (Settings → System settings → WebHook → наш endpoint) |
| Візит відбувся (attendance) | статус record-а в Altegio (адмін відмічає у своєму інтерфейсі як звик) |

**Авторизація:** `Authorization: Bearer <partner_token>, User <user_token>`. Отримати:
1. Partner token (доступ до API / маркетплейс Altegio)
2. User token користувача з потрібними правами
3. `company_id` кожної філії

### ⚠️ Перевірити на старті (Фаза 0, до написання коду)
1. **Тариф/доступ до API** — чи відкритий API на поточному тарифі салону.
2. **Улюбленці в Altegio** — чи доступні картки тварин через API (в документації явно не описано). Якщо ні → зберігаємо улюбленців у своїй БД, а в Altegio-записі передаємо ім'я/породу в коментарі.
3. **Loyalty API** — чи використовує салон бонусну програму Altegio і чи читається баланс по API. Якщо ні → власні таблиці бонусів (запасний варіант описаний у Фазі 6).
4. **Правило 24 год** — в Altegio є власне налаштування вікна онлайн-скасування; узгодити, щоб бот і сайт поводились однаково.

## Архітектурні рішення

### БД: Supabase (безкоштовний tier)
- **Supabase** = хмарний Postgres + веб-панель. Нічого не треба хостити самим; адміністратор може дивитись дані (улюбленці, оцінки) прямо в браузері.
- Підключення — **тільки через `supabase-py` (REST, HTTPS)**, НЕ напряму до Postgres: безкоштовний PythonAnywhere блокує сирі TCP-з'єднання (порт 5432), а HTTPS через проксі працює.
- Схему таблиць створюємо через SQL Editor у панелі Supabase (SQL-скрипт тримаємо в репо: `db/schema.sql`), тому SQLAlchemy/Alembic не потрібні.
- Ключі: `SUPABASE_URL` + `SUPABASE_SERVICE_KEY` у `.env` (service key, бо звертається тільки наш бекенд; Row Level Security можна не вмикати).
- Зберігає ТІЛЬКИ те, чого немає в Altegio (модель нижче).

### Scheduler: PythonAnywhere Scheduled Task → HTTP endpoint
- Endpoint `POST /cron/<CRON_SECRET>` у Flask, викликається кожні 10–15 хв (PythonAnywhere Scheduled Task на платному тарифі або безкоштовний зовнішній cron типу cron-job.org).
- Всі заплановані сповіщення — в таблиці `notifications` (`pending`/`sent`), рестарти нічого не гублять.

### Вебхуки Altegio: endpoint `POST /altegio/webhook`
- Приймає події record created/updated/deleted.
- Синхронізує стан: перепланувати нагадування при переносі, скасувати їх при видаленні запису, надіслати клієнту підтвердження якщо запис створив адміністратор по телефону.
- Перевірка автентичності (секрет в URL + звірка даних через API).

### UI бота: Inline-кнопки + ConversationHandler
- Головне меню — `ReplyKeyboardMarkup`; флоу (запис, анкета, оцінка) — `InlineKeyboardMarkup` + `CallbackQueryHandler` + `ConversationHandler`.
- Стан ConversationHandler in-memory; чернетка анкети додатково в БД (`draft_json`), щоб рестарт не втрачав прогрес.

### Ролі
- `ADMIN_GROUP_CHAT_ID` + `ADMIN_TOPIC_ID` у `.env` — усі сповіщення (низька оцінка, незаповнена анкета, "потрібна допомога") летять одним повідомленням у топік адмін-групи.
- Адмін-функції в боті — мінімальні (фото до/після, рекомендації майстра). Все інше адміністратор робить в Altegio.

## Модель даних у Supabase (мінімальна)

```
clients        id, tg_user_id (unique), altegio_client_id, phone, name,
               registration_done (bool), draft_json (чернетка анкети),
               last_promo_at (anti-spam)

pets           id, client_id → clients, name, breed, birth_date, weight,
               allergies, behavior_notes, photo_file_id,
               rabies_vaccine_date, vaccine_photo_file_ids (json),
               altegio_pet_id (nullable — якщо Altegio віддає тварин по API)

tracked_records id, altegio_record_id (unique), client_id, pet_id,
               starts_at, service_title, location_title, status,
               raw_json (останній стан з Altegio/вебхука)
               -- локальний "кеш" записів: щоб планувати нагадування
               -- і зв'язувати запис ↔ улюбленець ↔ оцінка

visit_extras   id, altegio_record_id, groomer_recommendations (text),
               next_visit_weeks (int), photo_before_ids (json), photo_after_ids (json)
               -- те, чого в Altegio немає: фото до/після + рекомендації майстра

ratings        id, altegio_record_id, service_stars (1–5), groomer_stars (1–5),
               comment, created_at

notifications  id, client_id, type (reminder_2h / thanks_rating / rebook_nudge /
               birthday / vaccine / form_incomplete / custom),
               payload_json, send_after, status (pending/sent/failed), sent_at

chat_messages  id, client_id, role, content, created_at
               -- історія AI-чату (переживає рестарти, обрізаємо до ~20 останніх)
```

Telegram-фото зберігаємо як `file_id` (Telegram тримає файли вічно).
Записи, слоти, послуги, ціни, бонуси — **НЕ дублюємо**, читаємо з Altegio (крім легкого кешу `tracked_records` для нагадувань).

### ⬜ Фаза 11 — Вибір конкретного грумера при записі

Розширення флоу `📅 Записатись`/`💰 Дізнатись вартість` (Фаза 2): новий крок вибору майстра одразу після локації, перед категорією послуг.

**Дизайн:**
1. Після вибору локації — список майстрів філії (`altegio.get_staff(company_id)`), карткою `name` (поле вже містить рівень прямо в самому імені, напр. `"PRO грумер Саша"`, `"ТОП грумер Тимур"`, `"Грумер Влада"` — так завела сама точка продажу, окремого показу рівня не треба) + кнопка `🎲 Будь-який спеціаліст`.
   - ⚠️ Перевірено наживо (2026-07-21): поле `specialization` зі `get_staff()` інколи не збігається з рівнем у `name`/`position.title` (напр. майстер `"ТОП грумер Дарина"` має `specialization: "Грумер"`, але `position.title` і фактична приналежність до категорій прайсу — «Топ грумер», звірено через `staff` у `get_service_categories()`). `specialization`, схоже, застаріле й не використовується для реального рівня — для показу довіряти `name`, для фільтрації послуг/цін — тільки `staff` у категоріях, не `specialization`.
2. **Обрано конкретного майстра** (`staff_id != 0`):
   - Категорії/послуги фільтруються до тих, де `staff_id` є в полі `staff` категорії з `get_service_categories()` (те саме поле вже використовує логіка sibling-рівнів з breed-fallback, Фаза 2).
   - `book_dates`/`book_times` викликаються з конкретним `staff_id` замість `0` — слоти лише цього майстра.
   - На підтвердженні `find_available_staff_for_slot()` не потрібен — `staff_id` вже відомий, `create_record()` викликається напряму з ним.
3. **Обрано «Будь-який спеціаліст»** — поведінка як зараз, без змін: усі категорії, усі послуги, `staff_id=0` для дат/часів, `find_available_staff_for_slot()` резолвить майстра на підтвердженні.

**Відкрите питання:** якщо конкретний майстер не має жодної послуги, що підходить під породу улюбленця (breed-fallback, Фаза 2) — пропозиція «є на іншому рівні» тут сенсу не має (клієнт свідомо обрав саме цього майстра), тож одразу показувати лише «Інші породи» за вагою + повний прайс цього майстра, без кнопок переходу на інший рівень.

**Критерій готовності:** клієнт бачить список майстрів з рівнями (з `name`) → обирає конкретного → бачить тільки його послуги і вільні слоти → запис створюється саме на нього без резолву на підтвердженні; «Будь-який спеціаліст» лишає поточну поведінку без регресій.
